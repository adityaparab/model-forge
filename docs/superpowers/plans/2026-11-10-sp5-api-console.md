# SP5: API, Console, Tracing and the Demo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put a FastAPI control plane and a React console over the governed run, trace it end to end into Jaeger and Phoenix, add pause, replay from the console (manual and on seal), cost tracking and server-side settings, and make `make demo` bring the whole stack up with the Polish brief running in it.

**Architecture:** `packages/api` (`modelforge_api`) reads lineage and the LangGraph checkpoint through the orchestrator's new `inspect` module, writes approvals, pauses, resumes, aborts and replays by enqueueing for the worker (it never runs the graph or calls a model), streams the hash-chained events over SSE by polling, and serves the built console as an SPA. `modelforge_lineage.tracing` owns the OpenTelemetry provider; the worker, `Step`, the tool client and the gateway open spans under one trace per run. The console (`console/`, React 19, Vite, TanStack Query, Tailwind v4) talks only to `/api/v1` with types generated from the API's OpenAPI document and tests over fixtures captured from a fake run.

**Tech Stack:** Python 3.12 (uv workspace), FastAPI, uvicorn, OpenTelemetry SDK with the OTLP/HTTP exporter and the FastAPI instrumentor, psycopg 3, LangGraph 1.2 (unchanged), Typer, pytest; Node 22, React 19, Vite, TypeScript strict, TanStack Query, React Router, Tailwind CSS v4, react-markdown, Vitest, React Testing Library, openapi-typescript; Docker Compose with Postgres, Jaeger 2 and Arize Phoenix.

**Spec:** `docs/superpowers/specs/2026-11-10-sp5-api-console-design.md` (binding); umbrella `docs/superpowers/specs/2026-11-09-modelforge-architecture-design.md` sections 4.2, 4.3, 4.4, 10.5, 11, 12, 13, 15, 20, 21; `docs/superpowers/notes/2026-11-10-sp4-handoff.md`.

## Review Focus

Inputs the spec implies but no task's tests exercised until the lines below were added to their owning tasks:

1. A `Last-Event-ID` header that is not an integer, or larger than the run's head, must start the stream from the beginning (run stream) or the head (global stream), never fail. Pinned in Task 13.
2. A brief body that is not UTF-8, or larger than 1 MiB, must answer `400` kind `brief`, never `500`. Pinned in Task 12.
3. An identity header of whitespace only, of 65 characters, or containing a space must answer `401`; `alice.b@example.org` is accepted. Pinned in Task 9.
4. `GET /costs` with `since` after `until` must answer `400` kind `validation`. Pinned in Task 14.
5. A pause requested after the last node has started (the run finishes before any node reads the flag) must leave the run in its final status with the flag cleared, so the run's next execution is unaffected. Pinned in Task 6.
